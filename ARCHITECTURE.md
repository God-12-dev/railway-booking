# RailConnect Architecture

## Project state

The workspace initially contained no application or database project. The application is now implemented across the twelve planned work areas. The source includes a Next.js App Router app, PostgreSQL/Prisma persistence, seed data, Argon2id authentication, session-based authorization, booking and admin workflows, localized landing and auth experiences, and delivery documentation. Type checking, linting, unit tests, and a production build are being validated in the current environment. PostgreSQL is not available here, so migrations, seed execution, and end-to-end database transactions have not been run against a live database.

## Product boundary

RailConnect is an academic railway reservation demonstration. All train availability, booking, payment, PNR, tracking, refund, and food-order data are seeded or simulated. The UI and ticket state that they are not valid railway reservations. No IRCTC connection, real payment collection, or real-time GPS is included.

## Architecture

- **Web app:** Next.js App Router, TypeScript, Tailwind CSS, responsive server-rendered pages with client components for interactive forms.
- **Persistence:** PostgreSQL through Prisma. Relational constraints and serializable transactions protect booking and seat allocation.
- **Authentication:** Argon2id password hashes, random database-backed sessions (only the SHA-256 token hash is stored), server-side role checks, and session invalidation on deactivation.
- **Validation:** Zod schemas at API and form boundaries; mutations repeat authorization and ownership checks.
- **Business modules:** authentication, catalog, search, seat holds, bookings, payments, tickets, tracking, food, notifications, and administration.
- **UI:** shared responsive components, dark/light theme, English/Hindi/Kannada message catalogs, Recharts analytics, Leaflet/OpenStreetMap route display, React PDF tickets, and next-intl.
- **Operations:** environment example, Prisma migration/seed scripts, unit and browser tests, setup and deployment guidance.

## Data and booking integrity

The schema covers users, stations, trains, routes, schedules, stops, fares, coaches, seats, seat holds, bookings, passengers, assigned seats, payments, cancellation/refund records, food orders, tracking, notifications, reviews, lookup attempts, and audit logs. Fare and passenger-seat assignment are computed on the server. Holds have expiry, active-inventory partial unique indexes protect concurrent allocations, and payment confirmation/cancellation are transaction-based. PNRs are generated by the server. Card details are never collected or stored.

## Phased implementation record

1. **Inspection and architecture:** Confirmed an empty starting workspace and documented product boundaries and the delivery sequence.
2. **Foundation:** Next.js/TypeScript scaffold, dependencies, Prisma/PostgreSQL schema and migration, sample seed, Argon2id credentials, opaque database sessions, and protected account pages.
3. **Design foundation:** Responsive shell, shared UI primitives, theme and locale preferences, translated landing page, and route search entry.
4. **Rail catalog:** Station, train, route, schedule, coach, and seat management APIs and administrator interfaces; soft archival and audit records.
5. **Search:** Validated route/date/class/passenger search, availability/fare results, filters, sorting, and train detail.
6. **Inventory:** Coach seat map, expiring seat holds, ownership checks, and serialized inventory validation.
7. **Booking:** Passenger forms, server-side fare, booking draft, simulated payment outcomes, berth-preference assignment, and confirmation.
8. **Tickets and account:** Ticket PDF, protected PNR lookup, booking history, cancellation/refund simulation, dashboard notifications, and booking status.
9. **Journey services:** Seeded simulated tracking and route visualization, food catalog and database-backed demo orders.
10. **Administration:** Analytics, schedule/inventory/user/booking/food management, role protections, and audit log views.
11. **Polish:** Persistent locale/theme selection, English/Hindi/Kannada landing and account messages, responsive controls, and form/accessibility refinements. Some deeper operational/admin copy remains English.
12. **Quality and delivery:** Unit/browser test suites, type/lint/build commands, deployment scripts, environment setup, limitations, and operator documentation.

## Verification boundary

Unit tests cover fare/refund calculations, berth assignment, schema validation, and India-time date ranges. Browser tests exercise landing search controls and locale/theme persistence. PostgreSQL-backed flows require `DATABASE_URL`, migrations, and sample data before they can be run end to end. No live railway, payment, or GPS integration is part of this project.
